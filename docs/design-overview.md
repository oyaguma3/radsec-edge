## 1. 位置づけ

本PoC は RADIUS（UDP）だけを受け、RadSec はスコープ外である（D-01）。AP と RadSec でつなぐときは、radsecproxy を前段に置いて、証明書で AP を識別し、NAS-Identifier を AP ごとの値に置き換える（D-08 §5.8）。この方式を、本PoC から切り離した独立のノードとして作り、Web GUI と API で運用できるようにしたものがエッジである。

- エッジは、AP のグループ（テナント）ごとに radsecproxy のコンテナを立て、その設定と起動・停止を制御する。
- 1 つのテナントを複数のエッジに置く（冗長化、地域）。エッジも複数置く。
- AP の証明書（クライアント証明書）とエッジのサーバー証明書は、エッジの外の独立CA が発行する。エッジは CA の鍵を持たない。
- エッジは単独モード（エッジの GUI だけで運用する）と管理モード（OSS/BSS から provisioner を通して運用する）を持つ。単独モードから作り、管理モードを後で足す（§6）。

```
                            中央（WireGuard のハブ）
  [ブラウザ] ─Cloudflare Access─> OSS/BSS ─mTLS─> provisioner ─mTLS─┬─> 本PoC（Provisioning API）
  （テナントの利用者・運用者）                                       ├─> aka-only-server
                                                                     ├─> CA（radsec-ca）
                                                                     └─> エッジ 1..n（トンネルの中）
  本PoC（auth-server / acct-server）<── RADIUS（UDP。トンネルの中）──┐
  CA の CRL（HTTP。トンネルの中）───────────────────────────────────┤
                                                                     │ WireGuard（エッジから外向きに接続）
                     ┌───────────────────────────────────────────────┴──────┐
                  エッジ 1                                               エッジ 2
       radsecproxy（テナント A）:20831                        radsecproxy（テナント A）:20831
       radsecproxy（テナント B）:20832                        radsecproxy（テナント C）:20833
                     ▲ RadSec（TCP。公開の受信はここだけ）                 ▲
                AP（テナント A・B）                                   AP（テナント A・C）
```

### 1.1 なぜテナントごとにコンテナを分けるか

| radsecproxy 1 台の弱点 | テナントごとのコンテナにすると |
|---|---|
| AP の追加・変更には再起動が要り（SIGHUP で読み直すのは CA と CRL だけ。D-08 §5.8）、全 AP の接続が切れる | 切れるのはそのテナントの AP だけ。テナントを複数のエッジに置けば、エッジを 1 台ずつ反映して、AP はもう一方のエッジにつなぎ替えられる（§11.4） |
| 送信元 IP の範囲が重なる client は同じ tls ブロックを参照する必要があり、CA をテナントごとに分けられない | テナントごとの CA だけを信頼させられる。テナント A の CA が発行した証明書では、テナント B のポートにつながらない |
| 設定が 1 つに膨らむ | テナントごとの小さな設定になり、生成・検証・戻しが局所で済む |

## 4. 技術方針

PoC セットの他の Go のリポジトリと同じ流儀にそろえる。

- 言語: Go 1.27.2。標準ライブラリを優先する（`net/http` のメソッドつき ServeMux、`html/template`、`text/template`、`embed`、`log/slog`、`encoding/json/v2`、`crypto/x509`、`crypto/tls`）。
- 外部依存（Go）: SQLite のドライバー（§19 の 5）。Docker Engine の API は、公式の SDK を使わず、unix ソケットへの HTTP で必要な口だけを呼ぶ（依存を増やさない）。
- 画面: OSS/BSS と同じ Go + htmx + daisyUI（JavaScript は書かない）。OSS/BSS の画面の土台と Cloudflare Access の JWT の検証をコピーして手直しする（共有モジュールにはしない）。
- リポジトリ: エッジは `radsec-edge`（module パス `github.com/oyaguma3/radsec-edge`）。CA は別のリポジトリ `radsec-ca` にする（§19 の 7。作業ディレクトリは `~/projects/radsec-ca`）。CA の詳しい設計は `radsec-ca` の設計概要に書き、本書には全体に関わることだけを残す。名前に eapaka を入れない（本PoC に依存しない汎用の部品として作る）。
- 設定は環境変数で受け取る。接頭辞はエッジが `EDGE_`、CA が `CA_`。
- 待ち受け（既存の 8443〜8446、9443〜9446 と重ならない）:

| 部品 | ポート | 待ち受けるアドレス | 内容 |
|---|---|---|---|
| エッジの Web GUI | 8447（HTTP） | compose のネットワークの中（cloudflared からだけ受ける） | 運用者向け（§13.1） |
| エッジの管理API | 9447（HTTPS、mTLS） | トンネルのアドレス | provisioner から（管理モード） |
| radsecproxy（テナントごと） | 20830〜20999（TCP） | ホストのすべてのアドレス | AP からの RadSec。テナントに全体で 1 つ割り当てる（§8） |
| CA の Web GUI | 8448（HTTP） | compose のネットワークの中 | 運用者向け |
| CA の API | 9448（HTTPS、mTLS） | トンネルのアドレス | provisioner から |
| CA の CRL の配布 | 8449（HTTP） | トンネルのアドレス | エッジから。CRL は署名つきで公開してよい情報なので、クライアント認証はしない |

- 配備: Docker Compose。エッジは `radsec-edge`、`radsec-edge-agent`、cloudflared と、テナントごとの radsecproxy（agent が作る）。CA は `radsec-ca` と cloudflared。
- イメージは公開しない（PoC セットと同じく、利用者はタグからソースでビルドする）。`radsec-edge` と `radsec-edge-agent` は 1 つのイメージ（distroless）に 2 つのバイナリとして入れ、compose で同じイメージを別のコマンドで動かす。radsecproxy のイメージは、Debian trixie のパッケージ（D-08 §5.8 で検証した 1.11.2）から `debian:13.7-slim` の上に作り、パッケージの版を書いて固定する。タグは `radsec-edge/radsecproxy:1.11.2-1-deb13u1`（パッケージの版 `1.11.2-1+deb13u1` の `+` はタグに使えないので `-` にする）。
- コードのコメントとドキュメントは日本語で書く。

## 5. 部品

### 5.1 エッジ

```
 ┌───────────────────────── エッジのホスト ─────────────────────────┐
 │ radsec-edge（権限なし）                                         │
 │   Web GUI（8447）・管理API（9447）・整合ループ・SQLite           │
 │        │ unix ソケット（決まった操作だけ）                       │
 │ radsec-edge-agent（docker.sock を持つ唯一の部品）                │
 │        │ Docker Engine API                                       │
 │ radsecproxy-<テナント>（テナントごと）                           │
 │   設定・CA・CRL・サーバー証明書を読み取り専用でマウント         │
 │ wg0（WireGuard。中央へ外向きに接続）                             │
 └───────────────────────────────────────────────────────────────────┘
```

| 部品 | 役目 |
|---|---|
| `radsec-edge` | テナントと AP の望む状態を持つ（単独モードでは正本、管理モードでは中央の写し）。設定を生成し、整合ループで反映する（§11）。Web GUI と管理API。radsecproxy のログを agent から受け取って、AP ごとの最後の接続などを出す。CRL を CA から取ってくる |
| `radsec-edge-agent` | Docker Engine を操作する唯一の部品。決まった操作だけを受け付ける（§10） |
| radsecproxy | テナントごとに 1 つ。AP の RadSec を受け、証明書で AP を識別し、NAS-Identifier を置き換えて、上流（本PoC など）へ RADIUS（UDP）で送る |

### 5.2 CA

詳しい作りは radsec-ca の設計概要に書く。ここでは役目だけを書く。

| 役目 | 内容 |
|---|---|
| CA の管理 | サーバーCA（1 つ）とテナントのクライアントCA（テナントごと。自己署名）を作る。鍵は暗号化して保存する（§9.4） |
| 署名 | CSR から公開鍵だけを使い、Subject・SAN・EKU・有効期限は CA が決める（§9.3） |
| 失効 | 証明書を失効させ、CA ごとの CRL を作り直して配布する |
| 画面 | 運用者向け（CA の一覧、証明書の一覧と失効、CRL の状態、監査ログ）。テナントの利用者は使わない（CSR は OSS/BSS の画面から出す） |
| API | provisioner から（管理モード）。単独モードでは運用者が CA の画面で署名し、結果をエッジの画面に取り込む |

## 6. モード

| 項目 | 単独モード | 管理モード |
|---|---|---|
| テナントと AP の正本 | エッジの SQLite | OSS/BSS（エッジの SQLite は写し） |
| テナントと AP の変更 | エッジの GUI（運用者） | OSS/BSS（テナントの利用者・運用者）から provisioner を通して。エッジの GUI では読むだけ |
| 運用の操作（状態、ログ、再起動、反映のやり直し） | エッジの GUI | エッジの GUI と、OSS/BSS（運用者） |
| 証明書 | 運用者が CA の画面で署名し、エッジの画面に取り込む | OSS/BSS が provisioner を通して CA に署名させ、エッジに送る |
| 名前とポートの割り当て | エッジが割り当てる | OSS/BSS が全体で割り当てる |
| エッジの台数 | 1 台（名前の一意を保証できないため） | 複数 |
| 中央が止まったとき | — | エッジは今の設定と最後に取った CRL で動き続ける（§14.7） |

- モードは環境変数 `EDGE_MODE`（`standalone` / `managed`）で決める。
- 単独モードから管理モードへ切り替えるときは、中央の宣言でエッジの状態を上書きする（エッジの既存のテナントを中央に引き継ぐ仕組みは作らない。§19 の 8）。
- 単独モードで作るデータの形は、最初から管理モードを前提にする（テナントの ID は外から与えられる形、名前の規則は全体で一意にできる形）。

## 7. データ

### 7.1 置き場所

| データ | 単独モード | 管理モード |
|---|---|---|
| テナント（名前、ポート、上流、配置） | エッジ | OSS/BSS（配置はエッジの台帳と合わせて持つ） |
| AP（名前、NAS-Identifier、SAN、証明書のシリアル番号と期限） | エッジ | OSS/BSS（エッジは写し） |
| エッジの台帳（接続先、容量） | — | OSS/BSS（接続先の証明書のフィンガープリントは provisioner の設定） |
| CA、発行した証明書、CRL | CA | CA |
| テナントのサーバー証明書の鍵 | エッジ（エッジで作り、外に出さない） | エッジ |
| 反映の履歴、コンテナの状態、AP の最後の接続 | エッジ | エッジ（中央は API で読む） |
| 利用者と権限 | エッジの運用者（Cloudflare Access のポリシー） | OSS/BSS（テナントの利用者を含む） |

### 7.2 エッジの SQLite（概要）

| 表 | 主な項目 |
|---|---|
| `tenants` | ID（管理モードでは OSS/BSS の値。単独モードでは slug と同じ。形は §8.1 の slug の規則）、名前（slug）、ポート、上流（認証・課金のホストとポート）、クライアントCA の証明書、CRL の取得先、サーバー証明書（鍵はファイル）、有効・無効、望む状態の版の番号、反映済みの版の番号 |
| `aps` | テナント、AP の名前、NAS-Identifier、CN、SAN（URI）、証明書のシリアル番号・期限（表示用。照合は CN と SAN で行う） |
| `applies` | テナント、版の番号、設定のハッシュ、操作（SIGHUP / 再起動）、結果、時刻、エラー |
| `crls` | テナント、最後に置いた CRL（番号、thisUpdate、nextUpdate、本体）、取得の状態（ETag、最後に試みた時刻と結果） |
| `audit` | 誰が（GUI の利用者のメールアドレス、または `X-Operator-Id`）、何を、いつ |

上流の共有シークレットはエッジごとに 1 つで、環境変数で渡す（§12.3）。

### 7.3 CA のデータ

CA のデータ（CA、発行した証明書、CRL、画面の利用者、監査ログ、冪等の記録）は、radsec-ca の設計概要 §8 に書く。

### 7.4 OSS/BSS の追加（概要）

| 表 | 主な項目 |
|---|---|
| `edges` | ID、名前、容量（テナントの数の上限）、状態（provisioner から） |
| `tenant_radsec` | テナント、slug、ポート、上流 |
| `placements` | テナント、エッジ、DNS のスロット（`primary` / `secondary` / `tertiary`。§8.3）、エッジに送った版の番号、反映の結果 |
| `aps` | テナント、AP の名前、NAS-Identifier、SAN、証明書のシリアル番号・期限 |

## 8. 名前と番号

### 8.1 規則

| 項目 | 形 | 例 | 一意の範囲 |
|---|---|---|---|
| テナントの slug | `^[a-z0-9]([a-z0-9-]{0,30}[a-z0-9])?$` | `tenant-a` | 全体 |
| AP の名前 | 同上（`probe` はヘルスチェック用に予約。§11.3） | `ap-001` | テナントの中 |
| NAS-Identifier | `<テナントの slug>-<AP の名前>` | `tenant-a-ap-001` | 全体 |
| AP の証明書の CN | NAS-Identifier と同じ（表示とログのため。照合には使わない。§10.3） | `tenant-a-ap-001` | 全体 |
| AP の証明書の SAN（URI） | `urn:<URN の接頭辞>:nas:<テナント>:<AP>` | `urn:example:nas:tenant-a:ap-001` | 全体 |
| テナントのポート | 20830〜20999 から 1 つ | `20831` | 全体（テナントを移しても変えない） |

- `-` が slug の中に入るので、NAS-Identifier だけからはテナントと AP の境目が決まらない。照合と表示には、テナントと AP の名前を別に持つ（`aps` の表）。
- 名前は設定ファイルと正規表現に入るので、上の規則で必ず検証してから使う（設定の書き換えの防止。§11.2）。
- ポートの範囲の大きさが、全体のテナントの数の上限になる（170）。

### 8.2 一意を誰が保証するか

- 管理モードでは OSS/BSS が保証する（エッジが複数でも、NAS-Identifier が衝突しない）。
- 単独モードではエッジが保証する。単独モードのエッジを複数置くと衝突しうるので、対象外とする（§2）。
- NAS-Identifier の衝突は安全面の問題になる。本PoC の認可ポリシーは `nas_id` の完全一致なので、別のテナントの AP に同じ名前があると、そのテナントの AP に自分のポリシーが当たる。

### 8.3 DNS

- テナントごとに、配置のスロットの名前を作る: `<スロット>.<テナント>.<ドメイン>`。スロットは `primary`・`secondary` の 2 つを基本とし、3 つ目が要るときは `tertiary` を使う（例 `primary.tenant-a.radsec.example.net`、`secondary.tenant-a.radsec.example.net`）。それぞれ、そのテナントを置いたエッジの公開のアドレスに向ける。
- AP には、`primary` を主、`secondary`（と `tertiary`）を予備の RadSec サーバーとして、テナントのポートとともに設定する。
- テナントを別のエッジに移すときは、そのスロットの DNS を書き換えるだけで済む（ポートは全体で割り当てているので変わらない）。
- DNS の登録は人が行う（対象外。§2）。OSS/BSS とエッジの画面に、登録すべき名前と向け先を出す。

## 9. 証明書と CA

### 9.1 CA の構成

| CA | 数 | 署名するもの | 誰が信頼するか |
|---|---|---|---|
| サーバーCA | 1 つ | テナントのサーバー証明書 | AP |
| テナントのクライアントCA | テナントごと（自己署名） | そのテナントの AP の証明書 | そのテナントの radsecproxy（全エッジ） |

- テナントのクライアントCA を共通のルートの下に置かないのは、radsecproxy にルートを信頼させると、別のテナントの証明書も検証を通り、テナントの分離が `matchCertificateAttribute` だけに頼ることになるためである（決定事項 7）。
- 管理API の mTLS（provisioner とエッジ・CA の間）の証明書は、CA では発行しない。PoC セットの他の部品と同じく、自己署名の証明書をフィンガープリントで照合する（`gen-client-cert` と同じ形）。

### 9.2 証明書の形

| 証明書 | 鍵 | Subject / SAN | EKU | 有効期限（案） |
|---|---|---|---|---|
| テナントのクライアントCA | ECDSA P-256 | CN `<テナント> client CA` | — | 10 年 |
| サーバーCA | ECDSA P-256 | CN `<組織> RadSec server CA` | — | 10 年 |
| AP の証明書 | AP が作る（ECDSA P-256 か RSA 2048 以上） | CN と SAN（URI）は §8.1 | clientAuth | 2 年 |
| テナントのサーバー証明書 | エッジが作る（ECDSA P-256） | SAN（DNS）`primary.<テナント>.<ドメイン>`・`secondary.<テナント>.<ドメイン>`・`tertiary.<テナント>.<ドメイン>` の 3 つ | serverAuth | 1 年 |

- テナントのサーバー証明書は、テナントとエッジの組ごとに発行する（鍵はエッジの外に出さない）。SAN には 3 つのスロットの名前をすべて入れるので、どのスロットに置いても、スロットの向け先が変わっても作り直さなくてよい。ワイルドカード（`*.<テナント>.<ドメイン>`）は使わない（radsecproxy をクライアントにした検証で、ワイルドカードをホスト名に一致するとみなさなかった。AP の実装によっても扱いが違いうる。§18.1 の V7）。
- 有効期限と鍵の種類は、AP の機種が受け付けるものを確かめて見直す（§18 の V7。実機の確認は後回しにした）。

### 9.3 署名の規則

- CSR から使うのは公開鍵だけとする（CSR の自己署名は確かめる）。Subject・SAN・EKU・有効期限は、登録済みの AP（またはテナントとエッジ）の情報から CA が決める。CSR に書かれた拡張は使わない（好きな SAN を書いた CSR による成りすましを防ぐ）。
- シリアル番号は 128 ビットの乱数にする。
- 証明書を更新するときは、同じ CN と SAN で新しい証明書を発行する。エッジは SAN の URI で照合するので、エッジの設定は変わらない。古い証明書は失効させる。
- 鍵を CA で作って配る方法（PKCS#12）は最初は作らない（§19 の 2）。

### 9.4 鍵の保管

- CA の鍵は SQLite に AES-256-GCM で暗号化して入れる。暗号化の鍵（KEK）はファイル（Docker の secrets など）で渡し、DB とは別に保管する。
- KEK と DB のバックアップの手順を、運用ガイドに書く。KEK を失うと、すべての CA を作り直し、すべての証明書を出し直すことになる。
- 署名は内部のインターフェース（`Signer`）の裏に置き、後で OpenBao の PKI や HSM に差し替えられるようにする（決定事項 6）。

### 9.5 CRL

- CA は、失効させたときと、一定の間隔（案: 1 日）で CRL を作り直す。次の更新の時刻（nextUpdate）は長め（案: 7 日）にする。
- エッジは、トンネルの中で CA の 8449 番（`GET /crl/{caId}.pem`。radsec-ca の設計概要 §7.3）から CRL を取りに行く（案: 5 分ごと。`If-None-Match` を付け、変わっていなければ 304 が返る）。配布の口はクライアント認証をしないので、CRL の改ざんは署名の確認で防ぐ。変わっていたら置き換えて、そのテナントの radsecproxy に SIGHUP を送る。
- 管理モードでは、失効の直後に provisioner がエッジに「すぐ取りに行く」よう指示する（§12.1 の `crl:refresh`）。間隔を待たずに反映できる。
- CRL の更新は、望む状態の版を上げない（運用者の変更ではないため）。今の版のディレクトリを写して CRL だけを入れ替えた版のディレクトリを作り、リンクを付け替えて SIGHUP を送る。
- 取得先の既定は `EDGE_CRL_BASE_URL` に `/crl/tenant.<slug>.pem` を足したもので、テナントごとに上書きできる。単独モードでは、画面から CRL の PEM を貼り付けて取り込むこともできる（CA に届かない環境のためと、段階 2 の CA ができる前の試験のため。取り込みの検証は取得と同じ）。
- 中央が止まって CRL を取れない間に nextUpdate を過ぎると、既存の接続は使えるが、新しい接続は拒否される（§18.1 の V2）。AP の再起動や回線の瞬断でつなぎ直した AP から順に使えなくなる。nextUpdate を長めにするのはこのためである。
- 期限の切れた CRL を読み込ませる（SIGHUP）と、既存の接続もすべて切れる（§18.1 の V2）。エッジは、取ってきた CRL の署名をそのテナントのクライアントCA の証明書で確かめ、番号が今の CRL より小さくないこと、nextUpdate が未来であることを確かめてから置き、過ぎていれば置かずに古い CRL のまま警告する（§11.2）。
- CRL の古さを監視する。エッジの `/status`（§12.1）と画面（§13.1）に、テナントごとの CRL の番号と nextUpdate を出し、残りが閾値（案: 3 日）を切ったら警告する。管理モードでは、OSS/BSS の中央の整合（§15）でも同じ値を見る。

## 10. radsecproxy のコンテナと agent

### 10.1 agent が受け付ける操作

`radsec-edge` と agent は unix ソケット（両方のコンテナで共有するボリューム）でつなぐ。agent が受け付けるのは次の操作だけとする。

| 操作 | 内容 |
|---|---|
| `EnsureTenant(id)` | テナントのコンテナを、固定のひな形から作る・起動する（あれば何もしない） |
| `Restart(id)` / `Stop(id)` / `Remove(id)` | 再起動・停止・削除 |
| `Signal(id, HUP)` | CA と CRL の読み直し |
| `Validate(id, 設定のディレクトリ)` | 捨てるコンテナで `radsecproxy -p` の構文検査を行う（§18.1 の V3。上流に届くネットワークで動かす） |
| `Status()` | ラベルのついたコンテナの一覧と状態（稼働、再起動の回数、起動の時刻） |
| `Logs(id, 行数)` | ログの末尾 |

### 10.2 コンテナのひな形（agent の中に固定）

- イメージは固定（`radsec-edge/radsecproxy:<パッケージの版>`）。
- マウントは `/var/lib/radsec-edge/tenants/<テナント>/` を `/conf` に読み取り専用で 1 つだけ。その中に版ごとのディレクトリ（`gen/<ハッシュ>/`）とシンボリックリンク `current`（`gen/<ハッシュ>` を指す）を置き、設定の中のパスは `/conf/current/...` で書く。bind mount の元のディレクトリを rename で差し替えても、動いているコンテナには古いディレクトリが見え続けるため（2026-10-18 に手元の Docker で確かめた）、マウントの中のリンクを付け替える（§11.1）。版のディレクトリは、今の版と直前の版を含めて 3 つ残す。
- Validate の捨てるコンテナには、検査する版のディレクトリを `/conf/current` に読み取り専用でマウントする（リンクを付け替える前に同じパスで検査できる）。
- ネットワークは、専用の bridge ネットワーク `radsec-edge-tenants`（internal でない。compose で名前を固定して作る）。`radsec-edge` もこのネットワークに入り、ヘルスチェック（§11.3）は `radsecproxy-<slug>:2083` につなぐ。Validate の捨てるコンテナも同じネットワークで動かす（上流に届く）。
- コンテナの名前は `radsecproxy-<slug>`。
- 公開のポートは、テナントのポートを 2083/tcp に。許した範囲（20830〜20999）の外は断る。公開するアドレスは agent の設定 `EDGE_AGENT_PUBLISH_ADDR`（空ならホストのすべてのアドレス）で、本番で公開のアドレスを 1 つに絞るときや、E2E でホストの中だけのアドレスにするときに使う（§22.2 の 1）。
- `cap_drop: ALL`、ルートのファイルシステムは読み取り専用、`no-new-privileges`、`privileged` は使わない（§18.1 の V9）。
- nonroot で動かし、UID と GID はホストで使われていない固定の値にする（`10083:10083`）。パッケージの利用者（UID 100）は、ホストの別の利用者（検証のホストでは `dhcpcd`）と重なりうるので使わない。
- エッジの部品の利用者: radsecproxy は `10083:10083`、`radsec-edge` は `10084:10083`、agent は `10085:10083` に docker.sock のグループ（`EDGE_DOCKER_GID`）を足したもの。テナントのディレクトリのファイルは、所有者を `radsec-edge`、グループを 10083 にし、ファイルは 0640、ディレクトリは 0750 にする（radsecproxy はグループで読む）。agent のソケットは 0660（グループ 10083）。
- init（tini）を PID 1 にする（Docker の `init: true`）。radsecproxy は PID 1 だと SIGTERM で止まらず、停止の猶予が切れて SIGKILL されるまで待つことになる（§18.1 の V6。init を使うと再起動は約 0.3 秒）。
- Docker のログは回転させる（`max-size`・`max-file`。案: 10 MB × 5）。AP の数が多いテナントでは、接続のたびにログが多く出るため（§10.3）。
- 再起動の方針は `unless-stopped`。ラベル `radsec-edge.tenant=<ID>`（と `radsec-edge.slug=<slug>`）で管理の対象を識別し、ラベルのないコンテナには触れない。
- API の要求からは、イメージ・マウント・権限を指定させない。`radsec-edge` が乗っ取られても、勝手なコンテナは作れない。

### 10.3 radsecproxy の設定（テナントごと）

D-08 §5.8 の検証の結果を、ひな形に入れる。

- `ListenTLS *:2083`。
- tls ブロックは 1 つ。`CACertificateFile` はテナントのクライアントCA だけ、`CertificateFile` / `CertificateKeyFile` はテナントのサーバー証明書、`CRLCheck on`、`TlsVersion TLS1_2:TLS1_3`。
- AP ごとに rewrite と client のブロックを作る（rewrite を先に書く）。AP の名前の順に並べ、ヘルスチェック用の `probe` の組を最後に置く（接続の少ない probe を後ろにして、AP の接続のたびの「一致しない」の行を増やさない）。
  - rewrite: `removeAttribute 32`、`addAttribute 32:'<NAS-Identifier>`、`supplementAttribute 1:'<NAS-Identifier>`（User-Name のない Accounting-On / Off 対策）。
  - client: `type tls`、`host 0.0.0.0/0`（IPv6 も受けるなら `::/0` も）、`certificateNameCheck off`、`matchCertificateAttribute SubjectAltName:URI:/^<SAN>$/`、`rewriteIn`。
  - probe の client ブロックにも、AP と同じ rewrite（NAS-Identifier `<テナント>-probe`）を付ける。probe は Status-Server しか送らない（radsecproxy が自分で応える）が、上流に届くものの NAS-Identifier を必ず置き換えるため。この値も NAS-Identifier の一意の確認（§8.2）に含める。テナント `a` の AP `x-probe` と、テナント `a-x` の probe（`a-x-probe`）のように重なりうるため、どちらの登録のときも断る。
  - 照合は SAN の URI だけで行う（CN は照合しない）。radsecproxy は、AP がつなぐたびに、一致するまでの client ブロックのそれぞれについて、照合した属性ごとに「一致しない」の行をログに出す（LogLevel 2 でも出る。500 台目の AP の 1 回の接続で、CN と SAN の両方を照合すると 998 行。§18.1 の V4）。CN も SAN も CA が登録の情報から決めるので、片方で足りる。
- server ブロックは上流の認証と課金（`type udp`、`statusServer on`）。`realm *` で両方に送る。上流の `host` は、ホスト名ではなく IP アドレス（トンネルの IP）で書く。radsecproxy は、起動のときに server のホスト名を引けないと終了する（§18.1 の V3）。
- `LogLevel 2` にする。LogLevel 3 は認証ごとの行と Status-Server の行が加わり、LogLevel 1 は拒否した証明書の CN も出なくなる（§18.1 の V4）。
- radsecproxy は `-f`（フォアグラウンド）で動かす。ログは標準エラーに出て、Docker のログで読める（`LogDestination` は無視される）。
- 正規表現に入れる値は §8.1 の規則で検証済みのものだけで、`.` など正規表現の記号は含まない（slug には英小文字・数字・`-` しかない）。

## 11. 反映（整合ループ）

### 11.1 流れ

```
変更（未反映として溜める）
 → 「反映」（単独モードは GUI のボタン、管理モードは API の apply）
 → 設定を生成（text/template。値は §8.1 で検証済みのものだけ）
 → 版のディレクトリ（gen/<ハッシュ>）に書き、agent の Validate で構文検査
 → シンボリックリンク current を原子的に付け替え（前の版は残す。§10.2）
 → 変わったのが CA・CRL だけなら SIGHUP、client ブロックやサーバー証明書なら再起動
 → ヘルスチェック（§11.3）
 → 失敗したら前の版に戻して再起動し、applies に記録する
```

- 最初の反映（前の版がない）で失敗したら、コンテナを止めて current を外す。外さないと、整合ループ（§11.5）が壊れた版で起動し直し続けるため。
- 反映済みの版の番号・設定のハッシュ・ポートを `tenants` に残す（`applied_version`・`applied_hash`・`applied_port`）。前の版に戻すときと整合ループは、反映済みのポートでコンテナを作る。
- 停止しているテナント（§11.5）の反映は断る（起動してから反映する。ヘルスチェックを省いた版を残さないため）。

- 変更を溜めてから反映するので、何件変えても再起動は 1 回で済む。GUI には「未反映の変更あり」と、設定の差分を出す。
- AP の削除は、証明書の失効と CRL の更新（SIGHUP）ですぐに効く。client ブロックは次の反映で消える（削除だけのために再起動しない）。

### 11.2 安全の決まり

- 設定ファイルに入る値は、すべて §8.1 の規則で検証する。上流のホストは IP アドレスだけ、ポートは数値だけ。
- `radsecproxy -p` で見つからない誤りは、エッジが設定を作る前に確かめる（§18.1 の V3）。
  - client の名前（と SAN）の重複（重複していても `-p` は通る）。
  - CA のファイルに CRL があること（`CRLCheck on` で CRL がないと、`-p` は通るが全 AP が拒否される）。
  - CRL の署名がテナントのクライアントCA で確かめられること、番号が今の CRL より小さくないこと（古い CRL への差し戻しを防ぐ）。
  - CRL の nextUpdate が未来であること（期限の切れた CRL を置いて SIGHUP すると全接続が切れる。§9.5）。
  - ヘルスチェック用の証明書（§11.3）が、今のクライアントCA で検証でき、期限の中にあり、今の CRL で失効していないこと。クライアントCA を差し替えて出し直していないと、反映の SIGHUP で AP の接続が切れたうえにヘルスチェックが通らず、前の版に戻すまで途切れるので、反映の前に断る（§22.4 の 1）。
- 設定はファイルの中身のハッシュで管理し、望む状態のハッシュと反映済みのハッシュを比べる。

### 11.3 ヘルスチェック

- テナントのクライアントCA の証明書・CRL・サーバー証明書・ヘルスチェック用の証明書がそろっていないテナントは、反映を断り、足りないものを画面に出す（ヘルスチェックを省いた反映はしない）。
- ヘルスチェック用の証明書を CRL で失効させたときは、その CRL も戻さずに置いて SIGHUP する（失効を優先する。ヘルスチェックが通らないことを理由に戻すと、以後そのテナントで AP の失効も効かなくなるため）。そのときは Status-Server を送らず、コンテナが動いていることだけを確かめる。画面とダッシュボードに出し直すよう出し、出し直すまで反映は断る（§22.4 の 2）。
- コンテナが稼働していること。
- テナントとエッジの組ごとにヘルスチェック用のクライアント証明書（予約した AP の名前 `probe`。利用者の AP には使わせない。CA のプロファイル `probe-client`）を発行する。鍵はエッジで作って外に出さない（§12.1 の `probe-csr`）。client ブロックは SAN（`urn:<接頭辞>:nas:<テナント>:probe`）で照合するので、テナントの中で 1 つで済む。エッジはこの証明書でTLS でつないで Status-Server を送り、応答を確かめる。radsecproxy は、クライアントからの Status-Server に自分で応える（上流には送らない。§18.1 の V5）。TLS のハンドシェイクが終わることだけでは足りない（証明書が client ブロックに一致しなくても、クライアントの側からは接続が確立したように見える）。

### 11.4 複数のエッジへの反映（管理モード）

- OSS/BSS は、テナントを置いたエッジに 1 台ずつ反映する（1 台目のヘルスチェックが通ってから 2 台目）。再起動の間、AP は予備のサーバー（もう一方のエッジ）につなぎ替える（AP の機種による。§18 の V6）。
- 1 台目で失敗したら、2 台目には送らずに止め、OSS/BSS の画面に出す。

### 11.5 起動したときと一定の間隔

整合ループは、起動したときと一定の間隔（案: 1 分）で、SQLite のテナントとラベルのついたコンテナを突き合わせ、望む状態に戻す（ホストの再起動、手で止めたコンテナ、消えたコンテナ）。無効にしたテナントのコンテナは止める。

- 整合ループが戻すのは運用の状態だけで、未反映の変更は反映しない。反映済みの版（current）と反映済みのポートで、コンテナを作る・起動する。まだ反映していないテナントには何もしない。
- 停止・起動（画面の操作。`tenants` の `enabled`）は運用の状態で、望む状態の版を上げない。操作したらすぐにコンテナに効かせる。停止したテナントは、整合ループも起動しない。
- Docker が再起動の方針で起動し直している途中のコンテナには触れない。
- SQLite にないテナントのコンテナ（ラベルのあるもの）とディレクトリは片付ける。

## 12. API

項目の詳細は OpenAPI（`docs/openapi/`）で定める。本書では口の一覧と方針だけを書く。

### 12.1 エッジの管理API（管理モード。9447、mTLS）

- 認証: provisioner のクライアント証明書のフィンガープリントを許可の一覧（`EDGE_ADMIN_CLIENTS`）で照合する。単独モードでは待ち受けない。
- ヘッダー: `X-Operator-Id`、`X-Trace-ID`、変更には `Idempotency-Key`（PoC セットと同じ）。
- 宣言的に扱う。中央は望む状態を PUT し、エッジは版の番号と反映の結果を返す。同じものを何度送っても結果は同じになる。

| 口 | 内容 |
|---|---|
| `GET /status` | モード、版、agent の状態、容量（テナントの上限と使用数）、トンネル、テナントごとの CRL の取得の状態・番号・nextUpdate（§9.5） |
| `GET /tenants` / `GET /tenants/{tenantId}` | テナントの望む状態、反映済みの版、コンテナの状態、設定のハッシュ |
| `PUT /tenants/{tenantId}` | テナントの作成・変更（slug、ポート、上流、クライアントCA、CRL の取得先） |
| `DELETE /tenants/{tenantId}` | テナントの削除（コンテナを止めて消す） |
| `POST /tenants/{tenantId}/server-csr` | テナントのサーバー証明書の鍵を作り、CSR を返す（鍵はエッジの外に出さない） |
| `PUT /tenants/{tenantId}/server-cert` | 署名済みのサーバー証明書を置く |
| `POST /tenants/{tenantId}/probe-csr` | ヘルスチェック用の証明書の鍵を作り、CSR を返す（鍵はエッジの外に出さない。§11.3） |
| `PUT /tenants/{tenantId}/probe-cert` | 署名済みのヘルスチェック用の証明書を置く |
| `GET /tenants/{tenantId}/aps` / `PUT` / `DELETE /tenants/{tenantId}/aps/{apName}` | AP の写しの一覧・作成と変更・削除 |
| `POST /tenants/{tenantId}/apply` | 反映（§11.1）。結果は `GET /tenants/{tenantId}` の反映済みの版で見る |
| `POST /tenants/{tenantId}/crl:refresh` | CRL をすぐ取りに行く |
| `POST /tenants/{tenantId}/restart` | コンテナの再起動（運用の操作） |
| `GET /tenants/{tenantId}/logs` | ログの末尾 |
| `GET /tenants/{tenantId}/last-seen` | AP ごとの接続の状態と最後の接続・切断の時刻（ログの `TLS connection from ... up` と `connection from ... lost` の行から作る。`/aps/{apName}` と重ならないよう `aps` の外に置く）。エッジは 1 分ごとに agent からログの続き（前回の時刻より後）を読んで SQLite に残す。コンテナを再起動すると切断の行は出ないので、コンテナの起動より前の接続は切れたものとして扱う。証明書の拒否の行は持ち主を CN からしか決められないので、最後の拒否の時刻として残すだけにする（§22.2 の 6） |

### 12.2 CA の API と配布の口

詳しくは radsec-ca の設計概要 §9（管理API）と §7.3（配布の口）に書く。本書の流れに関わる口は次のとおり。

| 口 | 呼ぶもの | 内容 |
|---|---|---|
| `POST /cas`（9448、mTLS） | provisioner | テナントのクライアントCA（ID `tenant.<slug>`）の作成。サーバーCA（ID `server`）は CA の初期化のときに作る |
| `GET /cas/{caId}`（9448） | provisioner | CA の証明書（エッジと AP に渡す） |
| `POST /cas/{caId}/disable`（9448） | provisioner | テナントをやめる（発行を止め、有効な証明書を失効させる。CRL は作り続ける） |
| `POST /certs`（9448） | provisioner | 発行。プロファイル（`ap-client` / `probe-client` / `tenant-server`）と名前の材料（テナント、AP またはエッジ）と CSR を渡す。署名する CA と CN・SAN は CA が決める |
| `POST /certs/{serial}/revoke`（9448） | provisioner | 失効（CRL をすぐ作り直す） |
| `GET /ca/{caId}.pem`・`GET /crl/{caId}.pem`（8449、HTTP） | エッジ | CA の証明書と CRL |

### 12.3 上流と共有シークレット

- エッジから本PoC へは、トンネルの中の UDP で送る。本PoC から見た送信元は、エッジのトンネルの IP になる（Docker のブリッジから wg0 へ出るときに送信元を書き換える。§18.1 の V8。テナントのコンテナは internal でないネットワークに置く）。radsecproxy の設定には、上流をトンネルの IP で書く（§10.3）。
- 本PoC には、エッジごとに `client:{エッジのトンネルの IP}` を 1 件登録する。共有シークレットはエッジごとに 1 つで、そのエッジの全テナントで共有する（送信元の IP が同じため）。
- 上流はテナントごとに設定できる形にしておく（本PoC 以外の RADIUS サーバーにも送れる）。既定値はエッジの環境変数で与える。

## 13. 画面

### 13.1 エッジの画面（運用者向け）

- 公開は OSS/BSS と同じく Cloudflare Tunnel と Access（ワンタイム PIN）で行い、エッジは JWT を検証する（§19 の 6）。許可するのは事業者の運用者だけで、テナントの利用者には開かない。エッジに Web の公開の受信は要らない（Tunnel は外向きに接続する）。

| 画面 | 内容 |
|---|---|
| ダッシュボード | モード、agent、トンネル、CRL の取得と期限（残りが閾値を切ったテナントの警告）、容量、未反映の変更のあるテナント |
| テナントの一覧・詳細 | ポート、上流、コンテナの状態、反映の履歴と差分、ログの末尾、再起動・停止・起動、DNS に登録すべき名前 |
| AP の一覧 | NAS-Identifier、SAN、証明書の期限、最後の接続 |
| 反映（単独モード） | 未反映の変更の差分と「反映」 |
| 証明書の取り込み（単独モード） | サーバーの CSR の取り出し、署名済みの証明書・CA の証明書の取り込み |
| 監査ログ | 誰が何をしたか |

管理モードでは、テナントと AP の変更の画面は読むだけになる（運用の操作はできる）。

### 13.2 CA の画面（運用者向け）

CA の一覧、証明書の一覧（期限の近いもの）、失効、CRL の状態（番号、次の更新）、単独モードのための CSR の署名（貼り付け）、監査ログ。公開はエッジと同じく Cloudflare Tunnel と Access で、許可するのは運用者の一部（CA の担当）だけにする。

### 13.3 OSS/BSS の画面（管理モード。追加）

OSS/BSS の役割（A テナントユーザー、B テナント管理者、C 運用担当、D システム管理者）に、次の権限を足す（案）。

| 操作 | A | B | C | D |
|---|---|---|---|---|
| 自分のテナントの AP の閲覧（NAS-Identifier、証明書の期限、最後の接続） | ○ | ○ | ○ | ○ |
| AP の登録（CSR の提出）・証明書の取り出し・更新 | × | ○ | ○ | ○ |
| AP の削除（失効） | × | ○ | ○ | ○ |
| 自分のテナントの反映 | × | ○ | ○ | ○ |
| テナントの RadSec の設定（slug、ポート、上流）と配置（エッジの選択） | × | × | ○ | ○ |
| エッジの台帳（追加・削除）、容量の設定 | × | × | × | ○ |
| エッジの運用の操作（再起動、ログ） | × | × | ○ | ○ |

- 認可ポリシーの `nas_id` には、A・B は自分のテナントの AP の NAS-Identifier だけを選べるようにする（他のテナントの AP を使わせるポリシーを書かせない。§19 の 9）。
- テナント管理者の反映が切るのは、そのテナントの AP の接続だけである（§1.1）。

## 14. 主な流れ（管理モード）

### 14.1 エッジの追加

1. ホストを用意し、WireGuard のピアを中央のハブに登録する。
2. エッジを導入し、管理API のサーバー証明書とフィンガープリントを作る。provisioner の設定にエッジ（ID、トンネルの URL、フィンガープリント）を足す。
3. OSS/BSS（D）でエッジを台帳に登録し、容量を決める。
4. 本PoC に、エッジのトンネルの IP を RADIUSクライアントとして登録する（OSS/BSS から provisioner の `/clients`）。共有シークレットをエッジの環境変数に渡す。

### 14.2 テナントの RadSec の有効化と配置

1. OSS/BSS（C・D）でテナントの slug を決め、ポートを割り当てる。
2. CA にテナントのクライアントCA を作らせる。
3. 容量を見てエッジを選び、スロットに割り当てる（必須の要件に合わせ、原則 `primary` と `secondary` の 2 台。3 台目は `tertiary`）。
4. 各エッジに `PUT /tenants/{id}`、`POST .../server-csr` と `POST .../probe-csr`、CA で署名（`tenant-server` と `probe-client`）、`PUT .../server-cert` と `PUT .../probe-cert`、`POST .../apply`。
5. 画面に出したスロットの名前を DNS に登録する。

### 14.3 AP の登録

1. テナント管理者（B）が AP の名前を入れ、AP が作った CSR を出す。
2. OSS/BSS が名前を検証し、NAS-Identifier と SAN を決め、provisioner を通して CA に署名させる。
3. 証明書を画面から取り出し、AP に入れる。AP には、スロット（`primary`・`secondary`。あれば `tertiary`）の名前、テナントのポート、サーバーCA の証明書も設定する。
4. OSS/BSS が、テナントを置いた全エッジに `PUT .../aps/{apName}` を送り、1 台ずつ反映する（§11.4）。
5. 認可ポリシーの `nas_id` に、この AP を選べるようになる。

### 14.4 AP の削除（失効）

1. OSS/BSS が CA に失効させ、全エッジに `crl:refresh` を送る（SIGHUP で効く）。
2. 全エッジの AP の写しを消す（client ブロックは次の反映で消える）。

### 14.5 証明書の更新

新しい CSR を同じ CN と SAN で署名し、AP に入れる。エッジの設定は変わらない。古い証明書を失効させる。

### 14.6 テナントの追加の配置・移動

新しいエッジに §14.2 の 4 を行い、スロットの DNS を書き換え、古いエッジから `DELETE /tenants/{id}` する。ポートは変わらないので、AP の設定は変えなくてよい。

### 14.7 中央が止まったとき

- エッジは、今の設定と最後に取った CRL で動き続ける。AP の認証は、本PoC が動いていれば通る。
- 止まっている間は、AP の追加・削除と失効の反映ができない。
- 中央が戻ったら、OSS/BSS がエッジごとに版を突き合わせて、ずれを直す（§15）。

## 15. 中央の整合

- 望む状態の正本は OSS/BSS にあるので、ずれを直すループは OSS/BSS に置く（§19 の 4）。一定の間隔で、配置ごとにエッジの `GET /tenants/{id}` の版の番号と設定のハッシュを読み、OSS/BSS の望む状態と比べる。ずれていれば、宣言を送り直して反映する。
- 宣言的な PUT なので、途中で失敗しても補償はいらない。次のループで送り直せばよい。
- provisioner は、エッジと CA への中継（`/edges/{edgeId}/...`、`/ca/...`）、冪等（`Idempotency-Key`）、操作の記録だけを受け持ち、望む状態は持たない（今の provisioner の「正本は下流」の方針のまま）。

### 18.1 段階 0 の結果（2026-10-18、simwifi）

構成: radsecproxy 1.11.2-1+deb13u1（Debian 13.7 の `debian:13-slim` にパッケージを入れたもの。OpenSSL 3.5.7）。エッジ側の radsecproxy をテナント A に 2 台（primary / secondary）、テナント B に 1 台、AP を 500 台分登録したテナント C に 1 台置いた。AP の役は radsecproxy をクライアントとして動かし、radclient で要求を出した。上流は、すべて受け付けて属性をログに出す小さな RADIUS サーバー（本PoC の代わり）。証明書と CRL は Go の `crypto/x509` で作った（将来の CA と同じ作り方）。ネットワークは外に出ない内部のもので、ホストにポートは公開していない。道具と手順は `verify/v0/`。

| # | 結果 | 判定 |
|---|---|---|
| V1 | SIGHUP で CA と CRL を読み直すと、既存の接続の証明書も検証し直し（`reverify result: ... certificate revoked`）、失効した AP の接続をその場で切る（`terminateinvalidclient`）。つなぎ直しも拒否される。失効していない AP の接続は切れない | 失効に再起動は要らない（§9.5、§14.4 のとおり） |
| V2 | 読み込んだ後に nextUpdate を過ぎた場合: 既存の接続は使えるが、新しい接続は `CRL has expired` で拒否される。期限の切れた CRL を読み込ませる（SIGHUP）と、既存の接続も全部切れる。AP の役は、もう一方のエッジにつなぎ替えて認証を続けた | 中央が止まったまま期限を過ぎると、つなぎ直した AP から順に使えなくなる。§18.2 の 4・5 |
| V3 | `radsecproxy -p` で構文検査ができる（正しければ終了コード 0、誤りは 1）。見つかる: rewrite が client より後ろ、正規表現の誤り、証明書のファイルがない、鍵と証明書が合わない、知らないオプション。**見つからない**: 同じ名前の client が 2 つ、`CRLCheck on` なのに CA のファイルに CRL がない（動かすと全 AP が `unable to get certificate CRL` で拒否される）。また、**server ブロックのホスト名を名前解決する**ので、引けないと `-p` も起動も失敗する（radsecproxy は起動のときに引けないと終了する） | §18.2 の 2・4 |
| V4 | `-f` のときログは標準エラーに出る（`LogDestination` は無視される）ので、Docker のログで読める。形は `Sat Oct 17 15:53:01 2026: 関数名: 内容`。接続: `tlsservernew: TLS connection from <IP>, client <名前>, subject CN=<CN>, TLSv1.3 ... up`、切断: `tlsserverrd: connection from <IP>, client <名前> lost`、拒否: `verify error: num=<番号>:<理由>:depth=0:CN=<CN>` の後に `SSL accept from <名前> (<IP>) failed`（**この名前は送信元 IP が一致した最初の client で、証明書の持ち主ではない**。持ち主は直前の行の CN で見る）。LogLevel 3 で `Access-Accept for user <利用者> from upstream-auth (...) to <client> (<IP>)` と Status-Server の行が加わる。LogLevel 1 では拒否した証明書の CN も出なくなる | §18.2 の 6 |
| V4（量） | k 番目の client ブロックに当たる AP がつなぐたびに、前の k−1 個の client について「一致しない」の行が CN と SAN の 2 行ずつ出る（LogLevel 2 でも出る）。500 台目の AP の 1 回の接続で 998 行。500 台の AP が全部つなぎ直すと約 25 万行 | §18.2 の 6 |
| V5 | AP からの Status-Server に、エッジの radsecproxy が自分で応える（`Access-Accept (response to Status-Server) from _self_`。上流には送らない） | ヘルスチェック用の証明書で死活を確かめられる（§11.3 のとおり） |
| V6 | radsecproxy はコンテナの PID 1 だと SIGTERM で止まらず、`docker restart` は停止の猶予（10 秒）が切れて SIGKILL されるまで待った。init（tini）を使うと 0.32 秒。primary の再起動の間、AP の役は secondary に切り替え、0.5 秒ごとの 80 件の要求はすべて成功した。primary に戻るまでは約 18 秒（AP の役のつなぎ直しの間隔が 2・4・8 秒と延びるため） | §18.2 の 3。実際の AP の振る舞いは V7 |

| V8 | WireGuard がないので未確認。Docker の規則は `-s <ブリッジのサブネット> ! -o docker0 -j MASQUERADE` で、bridge から出るパケットはどの出口（wg0 を含む）でも送信元が書き換えられる。テナントのコンテナは internal でない（外に出られる）ネットワークに置く必要がある | 段階 5 で WireGuard を使って確かめる |

### 18.2 設計への反映（2026-10-18 に合意し、本文に反映した）

1. テナントのサーバー証明書の SAN は、ワイルドカードをやめ、`primary` / `secondary` / `tertiary` の 3 つの名前を明示する（§8.3、§9.2）。3 つとも入れるので、どのスロットに置いても作り直さなくてよい。
2. radsecproxy の設定の上流（server ブロックの `host`）は、ホスト名ではなく IP アドレスで書く（§10.3、§12.3）。トンネルの IP なので固定でき、名前解決の失敗で起動しないことを避けられる。agent の Validate も同じ値で動く。
3. コンテナのひな形（§10.2）に init（tini）を入れる。UID はホストで使われていない固定の値（例 `10083`。鍵のファイルはその UID・GID だけが読める 0640）にする。
4. 反映の前の検証（§11.2）に、`-p` で見つからないものを加える: client の名前の重複、CRL があること、CRL の nextUpdate が未来であること。**期限の切れた CRL は置かない（SIGHUP しない）**。置くと全接続が切れるため、古い CRL のまま止めて警告する。
5. CRL の古さを監視する（§9.5、§15）: エッジの `/status` と画面に、テナントごとの CRL の nextUpdate を出し、残りが閾値（案: 3 日）を切ったら警告する。
6. ログ（§5.1、§12.1）: LogLevel 2 にする（認証ごとの行は出さない）。Docker のログの回転（`max-size`・`max-file`）を必須にする。AP の最後の接続は、接続の確立（`... up`）と切断（`... lost`）の行から作る。照合は SAN の URI だけにして（CN の照合をやめて）、「一致しない」の行を半分にする（CN も SAN も CA が登録の情報から決めるので、片方で足りる）。

## 19. 確認事項（2026-10-18 にすべて推奨案で合意）

1. テナントの分け方: ポートで分ける（推奨。§8）。テナントに全体で 1 つのポートを割り当て、移しても変えない。
2. AP の証明書: 最初は AP が作った CSR への署名だけにする（推奨）。鍵を CA で作って配る PKCS#12 は、Go の標準ライブラリに書き出しの機能がなく外部依存が要るので、対象の AP の機種が CSR を作れないと分かったときに足す。
3. エッジの画面の範囲: 運用者向けだけにし、テナントの利用者向けは OSS/BSS に置く（推奨。§13）。
4. 管理の経路と整合の置き場所: OSS/BSS → provisioner → エッジ・CA。provisioner は中継と冪等だけ、望む状態と整合のループは OSS/BSS に置く（推奨。§15）。
5. DB: エッジと CA は SQLite（推奨）。cgo の要らない `modernc.org/sqlite` を使う。OSS/BSS とそろえて PostgreSQL にすることもできるが、エッジのホストの部品が増える。
6. エッジと CA の画面の認証: OSS/BSS と同じ Cloudflare Tunnel と Access（推奨。JWT の検証のコードを流用でき、Web の公開の受信が要らない）。トンネルの中だけで開き、パスワードで認証する方法もある。
7. リポジトリ: エッジは `radsec-edge`、CA は別のリポジトリ `radsec-ca`（推奨。置く場所が中央とエッジで違い、CA は権限の境界を分けたいため）。同じリポジトリの 2 つのコマンドにすれば、作るのは早くなる。
8. 単独モードから管理モードへの切り替え: 中央の宣言で上書きし、引き継ぎはしない（推奨。§6）。
9. 認可ポリシーの `nas_id`: テナントの利用者（A・B）は自分のテナントの AP だけを選べるようにし、`*` は C・D だけが使えるようにする（推奨。§13.3）。今の OSS/BSS の認可ポリシーの画面の変更になる。
10. 有効期限（§9.2）と CRL の間隔（§9.5）の値: 案のとおり（AP 2 年、サーバー 1 年、CRL の作り直し 1 日・nextUpdate 7 日・取得 5 分）。V2 と V7 の結果で見直す。

### 22.3 通しの結果（2026-10-18、simwifi）

組み合わせ: radsec-edge（`scripts/e2e.sh` を足した作業ツリー。3-1 は `4e77a0a`）、radsec-ca `2ad5e0f`、本PoC `baa13f3`、eapaka_test `b3f8f25`。`scripts/e2e.sh` の確かめは、すべて通った。

- eapaka_test → AP の役の radsecproxy → エッジ → 本PoC で EAP-AKA の認証が通る。認可ポリシーは、エッジが置き換えた NAS-Identifier（`tenant-a-ap-001`）だけを許し、AP の役が名乗った値は本PoC に届かない。本PoC の auth-server のログでは、送信元が本PoC のネットワークのゲートウェイ（`172.20.0.1`）、NAS-Identifier が置き換えた値だった。
- Accounting-On が、置き換えた NAS-Identifier で本PoC の acct-server に届く。
- 画面の AP の一覧に「接続中」、失効の後に「証明書の拒否」が出る（AP の最後の接続。§12.1）。
- ほかのテナントの CA が発行した証明書では、テナントのポートに入れない（`unable to get local issuer certificate`）。
- CA で失効させ、エッジが CRL を取り直すと（SIGHUP）、その AP は認証できなくなる。同じ名前で発行し直した証明書では、エッジの設定を変えずにつながる。
- クライアントCA を差し替えてヘルスチェック用の証明書を出し直さずに反映すると、ヘルスチェックが通らず、前の版に戻る（戻した版のヘルスチェックも通る）。この確かめは、§22.4 の 1 を入れた後は「反映の前に断られ、AP の接続が切れないこと」の確かめに替えた。§22.4 の 2 の「ヘルスチェック用の証明書を失効させても CRL を置き、その後の AP の失効が効くこと」も足した。

通しで分かったこと（1・3・4 は設計を変えない。2 は §22.4 で直した）:

1. radsecproxy は、User-Name のない Accounting-Request を上流に送らず、自分で Accounting-Response を返す。エッジの置き換えの規則の `supplementAttribute 1`（§10.3）は、このために要る。E2E の AP の役も radsecproxy なので、AP の役を通すために Accounting-On に User-Name を入れて送った（エッジが補う動きは、この試験では確かめていない。本物の AP での確かめは V7 と同じく後回し）。
2. CA と CRL だけが変わる反映は SIGHUP で行う（§11.1）。radsecproxy は SIGHUP で既存の接続も検証し直す（§18.1 の V1）ので、新しい CA で検証できない AP の接続は、ヘルスチェックの前にその場で切れる。ヘルスチェックが通らなければ前の版に戻すが、その間（ヘルスチェックの上限の 10 秒と再起動）と、AP のつなぎ直しの間隔の分、接続が途切れる。
3. ヘルスチェック（Go の TLS のクライアント）は、radsecproxy が受け付ける CA の一覧に、ヘルスチェック用の証明書の発行者がないと、証明書を送らない。そのときの誤りは `tls: certificate required` になる。
4. Docker Desktop では、bridge のネットワークのゲートウェイの IP にポートを公開できないので、E2E は素の Docker（simwifi、GitHub Actions）で動かす。

### 22.4 通しで分かったことの確認事項（2026-10-18 にすべて推奨案で合意）

1. 反映の前に、ヘルスチェック用の証明書が今のクライアントCA で検証でき、期限の中にあることを確かめ、満たさなければ反映を断って画面に理由を出す（§11.2）。E2E の戻しの場面は「断られること」の確かめに替え、戻しそのものは Docker の結合の試験（失敗を注入するもの）で確かめる。
2. 新しい CRL にヘルスチェック用の証明書のシリアル番号が載っていたら、CRL は置いて SIGHUP し（失効を優先する）、Status-Server の確かめを省いてコンテナが動いていることだけを見る。画面とダッシュボードに出し直すよう出し、出し直すまで反映を断る（§11.3）。

### 23.2 確認事項（2026-10-18 に合意）

1. PoC セットのタグとの順番: provisioner と OSS/BSS の `main` は、pocset の残りの作業（定期の実行の確認、タグ付け）と同じなので、**pocset-v1.0.0 のタグを付け終えてから 4-2 に取り掛かる**（推奨案の「`main` に積む」は採らない）。4-1（radsec-edge）は先に進めてよい。
2. エッジの管理API は radsec-ca と同じ作りにする。パスに接頭辞を付けない（`/status`、`/tenants/...`）。クライアント証明書のフィンガープリントを `EDGE_ADMIN_CLIENTS` で照合する。変更の口は `Idempotency-Key` が必須（SQLite に 24 時間覚える）。ProblemDetails、`X-Operator-Id`、`X-Trace-ID`。サーバー証明書は自己署名で、`radsec-edge server-cert` で取り出す。単独モードでは待ち受けない。
3. 管理モードの画面は、テナント・AP・証明書・CRL の変更の操作を止めて表示だけにする。反映のやり直し・再起動・停止と起動・CRL の取り直し・ログは使える（§6 の運用の操作。停止と起動は緊急の操作として残す）。
4. 望む状態の版の受け渡し: OSS/BSS がテナントごとに版の番号（revision）を持ち、テナントと AP の宣言（PUT）に付けて送る。エッジは受け取った revision と反映済みの revision を `GET /tenants/{id}` で返す（エッジの `tenants` に列を足す）。中央の整合のループは、宣言が古ければ送り直し、反映が遅れていれば `apply` を呼ぶ（中央はエッジの設定のハッシュを計算できないため）。
5. AP の宣言は、AP ごとの `PUT` / `DELETE`（§12.1）に加えて、テナントの AP の一覧をまるごと置き換える `PUT /tenants/{id}/aps` を足す（中央の整合のループが 1 回で正しい状態に戻せるように）。
6. provisioner の下流の設定: CA は今の下流と同じ形（`PROVISIONER_CA_URL` とサーバー証明書のファイル）。エッジは `PROVISIONER_EDGES=<エッジの ID>=<URL>=<フィンガープリント>,...` で並べ、サーバー証明書はフィンガープリントで照合する。エッジと CA に見せるクライアント証明書は今の下流と同じもの。中継は中身を解釈せず、冪等・監査ログ・操作者の付け替えだけを行う（§15）。
7. OSS/BSS の段階 4 の範囲: AP の CSR の提出 → 署名 → 証明書の取り出しと、DNS に登録すべき名前の表示を画面で行う。CA とテナントの作成・配置は運用担当（C）とシステム管理者（D）、AP の登録・削除・反映はテナント管理者（B）以上（§13.3）。中央の整合のループの間隔の既定は 1 分。
8. コミットと push は、手順ごとに各リポジトリの `main` に行う。provisioner と OSS/BSS は、それぞれの CLAUDE.md の流儀（件名、契約テストの相手のコミットの更新）に従う。
